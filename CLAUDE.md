# Архитектура проекта

Акция «Купи и выиграй с Атемарской» (ТМ «Атемарская Ферма»). Проект собран по
образцу акции «Омский бекон»: тот же стек и те же подсистемы. Два отличия,
которые стоит держать в голове при любой доработке:

* **моментальные призы** — механика «лоток яиц», которой в проекте-образце не
  было (см. `docs/instant-prizes.md`);
* **лендинг из секций** — по образцу PromoTemplate: страница собирается из
  `{% include %}`, тексты секций лежат в БД, оформление — в CSS-токенах.

Проект = Django (бэкенд + шаблоны) + обычная статика. Отдельной сборки фронтенда
(Vite/SCSS) здесь нет: вёрстка своя, собирать нечего.

## Django

- Проектный пакет — `config`.
- Публичная часть — `main`, ядро акции — `promotion`, панель менеджера —
  `staff_panel`. Каждое приложение со своими `models.py` / `views.py` /
  `urls.py` / `services/`.
- Бизнес-логика, не относящаяся к HTTP-слою, живёт в `services/` соответствующего
  приложения — по одному файлу на сущность или сценарий, а не в `views.py`.
- Тестовый режим включается только через `.env`:
  ```
  DEBUG=True
  ```
  При `DEBUG=True` проект переключается на SQLite, локальный Redis и мок ФНС.
  По умолчанию (`.env` без `DEBUG` или `DEBUG=False`) — боевой режим:
  PostgreSQL, Redis в Docker, реальные интеграции.

## Шаблоны

- Каждая логическая секция лендинга — отдельный partial в
  `templates/partials/sections/`. Страница в `templates/pages/` — это набор
  `{% include %}`, а не монолитный HTML.
- Тексты секций хранятся в БД (`main.ContentBlock`) и правятся в админке.
  Лишняя секция выключается галочкой «Показывать», а не удаляется из шаблона.
- Повторяющиеся куски (модалки, карточки товаров и призов) тоже выносятся в
  partials, даже если используются один раз.
- Шапка и подвал общие для лендинга и кабинета: для участника это один сайт.
- Подключение SEO-сервисов (Яндекс Метрика, Вебмастер) — отдельными partials в
  `templates/seo/`, а не инлайном в `base.html`.
- Многострочные комментарии в шаблонах — только `{% comment %}`: `{# #}`
  работает построчно и в многострочном виде вываливается на страницу текстом.

## Оформление

- Все цвета, шрифты, размеры, радиусы и отступы — в
  `static/css/landing/tokens.css`. В шаблонах и остальных стилях фирменных
  значений и «магических» чисел нет: когда приедет брендбук, правится один файл.
- Стили блока живут рядом с блоком по смыслу, но в одном файле `landing.css` —
  отдельной сборки нет, дробить на десятки файлов без бандлера незачем.
- JS: один интерактивный компонент — один файл в `static/js/`.

## Правила акции в коде

Условия, которые легко перепутать при доработке, собраны в отдельных модулях —
они и есть единственная точка правды:

| Что | Где |
| --- | --- |
| Сколько призов может выиграть участник | `promotion/services/prize_limits.py` |
| Границы недельных и месячных периодов, даты розыгрышей | `promotion/services/promo_calendar.py` |
| Механика лотка яиц и расписание призовых моментов | `promotion/services/instant_prizes.py` |
| Минимальная сумма чека (в этой акции — нет) | `settings.PROMO_MIN_SUM_RUB` |
| Сроки акции и призовой фонд по брифу | `promotion/management/commands/seed_promo_calendar.py` |

Ни одно из этих условий не дублируется по месту использования: пулы розыгрыша,
панель менеджера и лендинг спрашивают эти модули, а не повторяют условие у себя.

## Тесты

```bash
python manage.py test promotion staff_panel main
```

Тесты — исполняемая документация условий акции: `test_prize_rules_audit.py`
сверяет бэкенд с брифом, `test_promo_calendar.py` — календарь с таблицей дат
розыгрышей, `test_instant_prizes.py` — механику лотка и равномерность выдачи
моментальных призов. Меняете условие акции — меняйте и тест, иначе неясно, что
именно было решено.
